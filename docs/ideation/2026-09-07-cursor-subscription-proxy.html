What changed since yesterday

Grounding Context

Codebase Context

otel-agent 是本地 LLM 网关：按 provider/model 前缀路由到 OpenAI 或 Anthropic REST。Provider 需要 base_url + api_key，或 auth: xai-oauth 且空 key。OpenAI 上游永远拼 {base}/chat/completions。VALID_AUTH_MODES 只有空和 xai-oauth。VALID_API_FORMATS 只有 openai | anthropic。旋转 token 放在 ~/.otel-agent/auth.json；resolve_bearer 只对 xAI 走 vault。代理绑 0.0.0.0。源码里没有 Cursor。

Past learnings

docs/solutions/architecture-patterns/import-supergrok-oauth-sidecar-vault.md：消费级订阅是个人 grant；旋转 refresh 不能写进 mtime 热加载的 YAML；从兄弟 CLI 拷贝，不要回写；在兄弟 CLI 不够用之前不要发明 device-code。xAI 不需要协议适配器——Bearer 已经能打 POST https://api.x.ai/v1/chat/completions（含 SSE）。

External context (2026-09-08)

  • 官方：Dashboard API Keys、agent login / CURSOR_API_KEY、Python/TS SDK、Cloud Agents REST、SDK Bridge（Connect/protobuf over HTTP/1.1；经典 gRPC/HTTP2 连不上）。
  • 官方原话：Cloud Agents API 与 SDK「are not a standalone model-inference or chat-completions API」。Help 里的 BYOK 是把 OpenAI/Anthropic key 填进 Cursor，方向相反。
  • 社区：cursor-agent-api-proxy、agent-cli-to-api 把 agent CLI 包成 /v1/chat/completions。cookie / IDE 逆向（cursor2api）仍然脆弱。

1 零代码配方：Dashboard key + 本地 OpenAI sidecar + YAML provider Recommended Low

Axis: runtime-bridge · Confidence: 88% · Complexity: Low

Description: 今天就能用、且最像 xAI 客户端体验的路径：在 cursor.com/dashboard/api 生成用户 API key（或 agent login），跑一个已经说 OpenAI 的本地适配器（社区 cursor-agent-api-proxy，或官方 CLI 的薄包装），然后在 otel-agent 里加一个普通 provider——name: cursor、base_url: http://127.0.0.1:4646/v1、api_key: crsr_… 或占位、api_format: openai。客户端继续 POST /v1/chat/completions，model 用 cursor/auto（或 agent --list-models 里的 id）。otel-agent 一行协议代码都不用写。

这是昨天 idea 1 与 idea 6 的合体，并纠正了「key 指向 api.anthropic.com」的错误。

Basis: direct: provider_utils.py:21 OpenAI 上游永远是 /chat/completions；任意 base_url 已可指向 localhost。external: Cursor docs/api 明确不是 chat-completions；cursor-agent-api-proxy 暴露 /v1/chat/completions。

Rationale: 「像 xAI」对你来说是 Hermes/OpenClaw 继续打网关。缺的那一跳放在 sidecar，而不是改网关的格式集合。

Downsides: 两个进程；社区包装可能随 CLI 破；用量走 Cursor 订阅池，和 IDE 抢配额。官方 SDK 才是长期适配器，社区包只是最快的今天。

2 先做 20 分钟官方 REST spike，取代昨天的 MITM Low

Axis: chat-completions-surface · Confidence: 90% · Complexity: Low

Description: 用刚生成的 crsr_ 打三个端点：GET https://api.cursor.com/v1/models、POST …/v1/chat/completions、POST …/v1/agents（及 Basic vs Bearer）。若 chat-completions 意外 200，idea 1 的 sidecar 可以删掉，变成「真 xAI 同构」。若只有 agents/SDK，就锁定 sidecar。这是昨天「30 分钟 MITM spike」在官方 REST 出现之后的廉价替代。

Basis: external: Cloud Agents 文档给了 api.cursor.com + Bearer/Basic；reasoned: 文档可能滞后，一次 curl 比写协议桥便宜两个数量级。

Rationale: 在写任何 otel-agent 代码之前，这是唯一能翻转「有没有推理 REST」的实验。

Downsides: 若 401/404，你只是确认了文档。不要把 spike 扩成抓包 IDE。

3 不要加 auth: cursor-oauth —— 「像 xAI」指的是前缀 + chat/completions Low

Axis: credential-lifecycle · Confidence: 86% · Complexity: Low

Description: 昨天 idea 2（Auth0 抽 token + vault）把 xAI 的手段当成了目的。xAI 需要 vault，是因为 SuperGrok access ~6h 且 refresh 会旋转，不能写进热加载 YAML。Cursor 的 dashboard key 是静态秘密；resolve_bearer 的非 oauth 分支已经返回 api_key。空 key 只对 xai-oauth 合法。保持 VALID_AUTH_MODES 不动。

Basis: direct: auth_vault.py:209-212；config.py:66-67, 185-188；learning「tokens rotate on refresh and cannot live in mtime-watched config.yaml」。

Rationale: 抄错抽象会让你为静态 key 再做一个 auth 模式，然后发现没有 token endpoint 可刷。

Downsides: 若 Cursor 以后只发短命 OAuth、停发静态 key，再开 vault。今天不要预支。

4 客户端仍走现有 OpenAI 路径，model 前缀 cursor/… Low

Axis: chat-completions-surface · Confidence: 84% · Complexity: Low

Description: 对齐 xAI 的 R2：OAuth/适配器是 auth 或 runtime 细节，不是第二个 provider 名。不要引入 cursor-oauth/… 或 cursor-grpc 作为客户端字符串。README 增加与 SuperGrok 并列的 curl：model: cursor/auto。

Basis: direct: plan 004 R2「Keep the client model prefix xai/…」；README.md curl 示例。

Rationale: 你已经在用 Hermes 打 otel-agent。改客户端字符串比加 sidecar 更痛。

Downsides: Cursor 模型 id（composer-2.5、auto-smart）和 OpenAI 名不同，需要一份短对照，而不是新 API 格式。

5 个人 grant 警告 + 用量池 403 改写 Medium

Axis: product-compliance · Confidence: 80% · Complexity: Medium

Description: SuperGrok 已经警告：订阅 token 是个人的，代理绑 0.0.0.0。Cursor SDK/CLI/Cloud Agent 走同一套用量池，和 IDE 抢配额。README 写清这一点；对 Cursor 上游的额度类 403，抄 xai_errors.py 改写并指向 cursor.com/dashboard/usage，不要当 circuit-breaker 失败。

Basis: direct: plan 004 R9；proxy.py host="0.0.0.0"；xai_errors.py；external: SDK 文档「SDK runs follow the same pricing, request pools」。

Rationale: 否则你会以为网关坏了，其实是 Cursor 月度池打满，而且可能把企业 key 暴露在局域网。

Downsides: 没有流量时改写器是死代码。可以先只写 README 警告，改写器跟在第一次真实 403 之后。

6 以后：sidecar 跟 proxy 同生命周期（像 dashboard spawn） Medium

Axis: runtime-bridge · Confidence: 72% · Complexity: Medium

Description: idea 1 稳定之后，才考虑 otel-agent proxy start 拉起/探活本地适配器，停的时候一起停。对标 dashboard 的 subprocess.Popen + pid 文件，以及 AGENTS.md 里「install 不 restart 仍是旧进程」的地雷。不要把 cursor-sdk 链进网关进程。

Basis: direct: commands/proxy.py / dashboard.py 已有 daemon spawn；AGENTS.md dashboard landmine。reasoned: 两个无文档进程撑不过 uv tool install --force .。

Rationale: 这是「网关产品」相对「自己拼两个命令」的增量。不是今天的阻塞。

Downsides: 生命周期、日志、Node vs Python 包装的成本。官方 Python SDK 在进程内跑 agent loop 会把 otel-agent 变成 Cursor 运行时——那是错误的产品边界（见拒绝表）。

7 若要自动登录：从 agent CLI / CURSOR_API_KEY 导入，不要发明 device-code Low

Axis: auth-acquisition · Confidence: 78% · Complexity: Low

Description: 昨天 idea 2/6 的正确后续不是 otel-agent auth cursor-login 再注册一个 OAuth app。兄弟 CLI 已经是 agent login。最多：读 CURSOR_API_KEY 或 CLI 的本地凭据，upsert YAML provider（静态 key）。xAI 的 device-code 是「没有 Hermes/Grok」时才加的第二刀。

Basis: direct: learning「Do not invent a new device-code client until import-from-sibling-CLI is insufficient」；plan 005 只在 import 不够时才做 RFC 8628。external: Cursor CLI 认证文档。

Rationale: 避免第二个 xai_oauth.py。Dashboard 复制 key 对个人订阅已经够用。

Downsides: CLI 凭据格式未探；可能只是环境变量。探明之前不要写导入器。
