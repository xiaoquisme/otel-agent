Grounding Context

项目: otel-agent — Python FastAPI LLM API 网关，使用 DuckDB 存储遥测数据（请求日志、token 用量聚合）。

核心问题: DuckDB 使用 OS 级文件锁，阻止多进程并发访问。代理进程写入 + Dashboard 进程读取会触发 IO Error: Could not set lock on file。

当前方案: 单写者架构 — 代理进程独占 DuckDB 写连接，Dashboard 通过代理 HTTP API 查询。Dashboard 独立运行时回退到空数据。

存储抽象: StorageBackend 基类，已有 DuckDBStorage 和 SQLiteStorage 实现。WAL 模式已启用。

查询需求: 分页查询、全文搜索、按时间范围聚合 token 用量（SUM/COUNT/GROUP BY）、模型排名。

相关文档: docs/solutions/concurrency/duckdb-multi-process-concurrency.md — 详细记录了 DuckDB 并发限制和单写者架构方案。

Topic Axes

  • 并发模型 — 数据库的多进程读写支持方式
  • 分析查询能力 — 聚合、分组、时间范围查询性能
  • 部署复杂度 — 嵌入式 vs 服务器模式，运维负担
  • 迁移成本 — 从 DuckDB 迁移的工作量和风险

并发模型 分析查询能力

1. PostgreSQL — 真正的多进程并发读写

Conf 90% Cx Medium
替换 DuckDB 为 PostgreSQL。PostgreSQL 原生支持多进程并发读写，MVCC 架构允许多个读者同时不阻塞写者。Python 生态有成熟的 psycopg2（同步）和 asyncpg（异步）驱动。聚合查询（SUM/COUNT/GROUP BY）性能优秀，且支持窗口函数用于模型排名。
external: Grafana、Prometheus、Datadog 等遥测/可观测性工具均使用 PostgreSQL 或兼容数据库存储指标数据。PostgreSQL 是业界标准的轻量级关系型数据库，支持真正的并发访问。
这是最直接解决并发问题的方案。当前 DuckDB 的单写者架构是 workaround；PostgreSQL 从根本上消除文件锁限制。Dashboard 可以直接读取数据库，无需绕道代理 HTTP API。存储抽象层（StorageBackend）已经存在，新增一个 PostgresStorage 实现工作量可控。
需要运行一个独立的 PostgreSQL 服务进程。对于个人/小团队项目，这增加了部署复杂度（需要 brew install postgresql 或 Docker）。但 SQLite 作为嵌入式备选仍然可用。
并发模型 迁移成本

2. SQLite WAL 模式优化 — 在现有架构内最大化并发

Conf 85% Cx Low
深度优化 SQLite 的 WAL（Write-Ahead Logging）模式。SQLite WAL 支持多进程并发读 + 单写者，且读操作不阻塞写操作。通过调整 PRAGMA wal_autocheckpoint、PRAGMA busy_timeout、PRAGMA synchronous=NORMAL 等参数，可以在保持单写者架构的同时大幅提升并发读性能。
direct: 项目已有 SQLiteStorage 实现（src/otel_agent/storage/sqlite.py:42），且已启用 WAL 模式（PRAGMA journal_mode=WAL）。当前 DuckDB 的单写者架构实际上和 SQLite WAL 的并发模型一致 — 问题不在模型本身，而在于 DuckDB 的文件锁过于严格。
这是最低成本的改进路径。不需要引入新依赖，不需要运行额外服务。SQLite WAL 的并发模型（多读者 + 单写者）恰好匹配当前的单写者架构。优化 WAL 参数可以让 Dashboard 直接读取 SQLite 数据库（无需绕道代理），同时代理继续写入。
SQLite 仍然只有一个写者。如果未来需要多进程写入，这条路走不通。聚合查询性能不如 DuckDB/PostgreSQL（但对当前数据量足够）。WAL 文件需要定期 checkpoint 以避免无限增长。
部署复杂度 并发模型

3. 单进程架构 — 从根源消除并发问题

Conf 75% Cx Low
将 Dashboard 完全合并到代理进程中（已经是部分实现），消除多进程访问数据库的需求。Dashboard 的 API 端点直接使用代理的 TelemetryLogger.storage 连接，无需 HTTP 代理路由。独立 Dashboard 命令保留为离线分析工具，但在代理运行时完全绕过。
direct: 项目已在 src/otel_agent/server.py:62 实现了共享存储：dashboard_api = DashboardAPI(telemetry.db_path, storage=telemetry.storage)。文档记录（docs/solutions/concurrency/duckdb-multi-process-concurrency.md）明确指出这是当前推荐方案。
这是已验证的方案，无需额外工作。消除了 DuckDB 锁冲突的根本原因 — 没有多进程，就没有文件锁问题。Dashboard 在代理进程内运行，共享同一个数据库连接。
Dashboard 无法独立于代理运行。如果代理崩溃，Dashboard 也随之不可用。对于需要独立部署 Dashboard 的场景（如远程监控），这不是长期方案。但这已经是你当前的架构 — 所以这个 idea 的价值在于确认：如果你的使用场景接受单进程，就不需要换数据库。
部署复杂度 分析查询能力

4. DuckDB HTTP Server 模式 — 保持引擎，改变访问方式

Conf 65% Cx High
使用 DuckDB 的 duckdb_server 或 motherduck 模式，将 DuckDB 作为 HTTP 服务暴露。多个客户端通过 HTTP 查询同一个 DuckDB 实例，由服务端管理并发。这保持了 DuckDB 的分析查询能力，同时避免了文件级锁问题。
reasoned: DuckDB 的并发限制来自文件级锁，而非查询引擎本身。如果通过一个中间服务层串行化所有数据库操作，多进程客户端就可以共享同一个 DuckDB 实例。这类似于 PostgreSQL 的连接池模式，但保持了 DuckDB 的嵌入式特性。
如果你特别看重 DuckDB 的分析查询性能（OLAP 优化、列式存储），这个方案保留了引擎优势。Dashboard 和代理都作为 DuckDB HTTP 客户端，由服务端协调并发。
DuckDB 官方的 HTTP server 模式仍处于实验阶段，生产稳定性未经验证。引入了额外的服务进程（和 PostgreSQL 方案一样需要运维），但生态成熟度远不如 PostgreSQL。实际上增加了复杂度而没有获得 PostgreSQL 的生态优势。
并发模型 迁移成本

5. 消息队列 + 只读副本 — 写入与查询解耦

Conf 60% Cx High
代理将遥测事件写入轻量消息队列（如 Redis List 或文件追加日志），后台进程从队列消费并写入数据库。Dashboard 从数据库读取，与写入完全解耦。写入路径无锁竞争，读取路径可以使用任意数据库。
external: ELK Stack（Elasticsearch + Logstash + Kibana）采用类似架构：Logstash 收集日志，Elasticsearch 存储和索引，Kibana 查询。生产级遥测系统（如 Jaeger、Zipkin）也使用队列解耦写入和查询。
彻底分离写入和读取路径，两者的并发模型独立演进。写入端可以使用任何追加结构（文件、Redis、Kafka），读取端可以用 DuckDB（分析查询）或 PostgreSQL（并发访问）。
对于个人项目的遥测代理来说过度工程化。引入了额外组件（队列 + 消费者进程），增加了运维复杂度。数据一致性变为最终一致性，查询可能有延迟。当前数据量（单用户 LLM 网关）不需要这种架构。
