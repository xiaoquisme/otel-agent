一句话结论

证据压倒性指向在既有 /v1/models 响应上加 additive 字段而非新开接口：收窄点唯一（aggregate_models）、仓库已有 body 级 additive 先例（errors 字段）、OpenRouter 已把「model 对象内扩展字段」做成行业事实标准；009 契约当年否决的是「custom format」而非 additive 字段。真正值得开会的不是「加字段还是新接口」，而是字段放哪、数据从哪来、谁校验——下文 1-5 号方向按此排序。

Grounding Context

Codebase Context

项目形态：Python 3.10+ FastAPI + httpx 的 LLM API 网关（otel-agent proxy），OpenAI/Anthropic 兼容；uv/hatch 打包 CLI；DuckDB（默认）/SQLite 存遥测；React+TS 前端；specs/ 001–020 为 spec-kit 规格驱动开发。

/models 现状：GET /v1/models（server.py:461）→ fetch_provider_models（models.py:59）按三条目录来源取模型：config 声明（config.py:110-121）、models_from vendor CLI（cli_models.py）、上游 GET /models 拉取；Cursor 环回走 sidecar CLI。ModelCache TTL 300s + config mtime 失效（models.py:15）。aggregate_models（models.py:158）把每个 entry 归一化为 {id, object, created, owned_by}，上游自带的任何额外元数据在此被丢弃（models.py:177-182）；body 级附加 errors 字段是既有先例（models.py:184-189，KTD6）。

既有契约决策（specs/009-models-api）：FR-010（spec.md:80）响应格式 MUST 遵循 OpenAI /v1/models 结构；SC-003（spec.md:93）OpenAI SDK client.models.list() 直接可用；SC-001（spec.md:91）cached <500ms。research.md:47 Decision 3 被否决的备选是「Custom format with more metadata: Rejected — breaks SDK compatibility」——被否的是「自定义格式」，additive 字段方案从未被讨论过（决定正文的「exactly」一词留下了文本争议，见方向 1）。contracts/models-api.md 锁定 entry 四字段；tests/test_models.py:106-120 断言的是字段存在而非四字段精确形状。

痛点/缺口：上游元数据被丢弃、能力/上下文长度没有任何可附着的结构位；三条目录来源只交换纯 id 字符串（声明与 CLI 路径 created: 0）；客户端已用 [500k]/[1m] 后缀表达上下文诉求但被 router.py:10-13 剥除（信息双向缺失）；全库无 context_length/max_output/capabilities 字段，属净新增概念；上游响应差异大（Codex 订阅端点返回空列表、Cursor 需走 CLI）；遥测侧已存 input_tokens/output_tokens/total_tokens（spec 020）。核验另发现一事实缺口：finish_reason 未落库。

Past Learnings（docs/solutions）

  • responses-chat-compat.md（high, 2026-09-23）：面向契约严格的客户端，响应字段「要么完整、要么整体省略」（缺值宁可不发）；不支持的能力要在调用上游前显式报错。
  • download-request-json-from-loaded-detail.md：能从既有响应派生的数据不要再开新路径；新路由可为 curl 保留但消费方须可降级——新路由还会在 :45638 长驻旧进程上 404（Dashboard CLI landmine）。
  • dashboard-render-delegation-pattern.md：格式知识单一来源；本仓库已有「新端点 + 既有响应加字段」双轨先例；跨层重复必然漂移（specs 011/012/018/020 回归四次）。
  • import-supergrok-oauth-sidecar-vault.md：引入新组件前先复用既有声明机制；模型 id 的 provider/ 前缀约定不可变。
  • integration-test-broken-after-sse-removal.md：变更清单必须枚举全部消费面（路由、前端、集成测试、文档）。

External Context

OpenRouter /api/v1/models 实测（2026-09-27，curl 一手验证，458 个模型）：model 对象内携带扩展字段已是行业事实标准——context_length: 200000、top_provider: {context_length, max_completion_tokens, is_moderated}、architecture: {modality, input_modalities, output_modalities, tokenizer}、supported_parameters: [...]。即「在 model 对象上加字段」有生态先例，且分层表达「名义上限 vs 实际可用上限」。

证据边界

外部广度调研部分缺失（web-researcher 超时、Anthropic 文档区域受限）。以下主张待核实，未作为任何存活方向的承重依据：Anthropic /v1/models 的 context_window/max_output_tokens、vLLM 的 max_model_len、LiteLLM model_info、vendor 的 1M 变体命名实践。

Ranked Ideas

  • 1. 在 /v1/models 响应上加 additive 能力字段（字段放哪的答案）
  • 2. 上游缺省时自动回填：OpenRouter 公共目录查询（整目录缓存）

1.在 /v1/models 响应上加 additive 能力字段——「加字段，不开新接口」

Confidence 85% Complexity Low direct + external 直接回答焦点问题
Description

在 aggregate_models 的归一化出口为每个 entry 附加 context_length、max_output_tokens（可选 top_provider 式子对象表达 provider 实际可用上限、supported_parameters 表达能力开关），OpenAI 四字段保留为 MUST 不动；拿不到可信值的模型整体省略这些字段，不填 null/0。字段命名对齐 OpenRouter 事实标准而非自造 schema。放置位置是本条的讨论子题：entry 内直加为主张（一次调用拿全，SDK 兼容有 OpenRouter 生态背书）；body 级 capabilities map 为保守备选（紧挨既有 errors 字段，entry 断言一行不改）；短期 opt-in 开关可作上线保险，但不建议做成默认形态（见淘汰表 M6）。

Basis

direct: models.py:177-182（唯一归一化收窄点，上游额外元数据在此被丢弃）；specs/009-models-api/research.md:47 被否决备选原文是「Custom format with more metadata」，additive 字段从未被讨论；body 级 additive 先例 models.py:184-189（docstring 明写 additive 不影响 data 消费者）。external: OpenRouter /api/v1/models 实测（2026-09-27）——model 对象内 context_length/top_provider/supported_parameters 已是行业事实标准，且生态对额外字段无感。

Rationale

用户问题的答案由三重证据钉死：收窄点唯一意味着改动是一处而非一套；仓库自己的 errors 字段证明「body 级 additive、消费者无感」在本项目已上线验证；OpenRouter 先例意味着这不是发明格式而是对齐格式，客户端生态已有解析这些字段名的代码。新开接口反而要求客户端两次请求并自行 join，还踩 :45638 旧进程 404 的 landmine。与方向 4 构成双向闭环：字段供后缀校验，后缀需求进遥测。

Downsides

009 决定正文的「exactly」一词对 additive 是否合规字面上未定论，需要一次契约修订签字（contracts 文档 + 契约测试同步改）；严格 schema 校验的客户端理论上仍可能对未知字段敏感（虽然 OpenRouter 生态反证了这一点）——「整体省略」纪律（responses-chat-compat 教训）是必须随行的保险。

2.上游缺省时自动回填：调用 OpenRouter 公共目录（整目录缓存，零配置）

Confidence 80% Complexity Medium direct + external（实测） 数据从哪来的答案（简化版）
Description

上游没给能力元数据时，直接查 OpenRouter 公共目录回填（/api/v1/models，无需鉴权，2026-09-27 实测可用）：一次拉取整个目录（458 个模型），按 ModelCache 模式整目录缓存（TTL 24h 级，每 TTL 窗口一次 HTTP，每模型只是本地查找），按模型 id 匹配后填 context_length / max_output_tokens（取 top_provider.max_completion_tokens）。来源链：上游/CLI 透传 → OpenRouter 回填 → 仍无则整体省略（不猜、不填 0）。匹配做小段归一化后精确匹配（xai↔x-ai、v-2.5↔v2.5、排除 :batch 变体），宁缺勿错。完全零配置：不设任何 config 声明入口，目录外模型（如 cursor 侧car）直接走省略纪律，不留手动兜底。

Basis

direct: models.py:177-182（元数据丢弃点 = 回填挂载点）；models.py:41-56（ModelCache 整目录缓存模式可直接复用）。external（实测）: OpenRouter /api/v1/models 2026-09-27——458 个模型、无需鉴权、字段即所需（xiaomi/mimo-v2.6-pro: context_length 1048576 / top_provider.max_completion_tokens 131072）；覆盖实测：xiaomi/mimo ✓、x-ai/grok ✓、openai/gpt-5.x-codex ✓、cursor ✗。reasoned: 一条 HTTP 换整目录，缓存成本近零；查询失败即省略，与「整体省略」纪律天然兼容。

Rationale

把「数据从哪来」从维护问题变成查询问题：零配置、零手写表，主流 provider 开箱命中（覆盖实测见 basis）。整目录缓存意味着回填几乎不增加延迟与外部依赖暴露面；每条元数据带 source: openrouter 标签（方向 3 的 provenance 口径），方向 5 的观测校验正好能抓「目录说 1M、你的部署其实 128k」这类背离。与方向 1 同构的「简单优先」：先用免费的行业公共数据把 90% 场景覆盖掉，长尾直接省略字段——省略本来就是既定纪律，不需要人为兜底。

Downsides

命名不一致是主要工程点：仓库 xiaomi/mimo-v-2.5 vs 目录 xiaomi/mimo-v2.5-pro、xai vs x-ai——需要归一化且只做精确匹配（模糊匹配填错比不填更糟）；cursor 侧car模型不在目录内——但按省略纪律这正是想要的行为（缺就是缺，不需要配置兜底）；OpenRouter 的数字是名义模型值，订阅档位不同的部署可能有出入（其 top_provider 分层恰好表达这一点）；引入一个第三方依赖——但失败路径只是省略字段，安全降级。

3.ModelCapabilities 单一出口管线：三来源结构化 + provenance + 消费面只读

Confidence 70% Complexity High direct + reasoned 杠杆最大的一条
Description

定义内部 ModelCapabilities 记录（context_length, max_input_tokens, max_output_tokens, source），把三条目录来源从「纯 id 字符串」升级为交换结构化能力卡（今天声明与 CLI 路径的 created: 0 空壳就是信息损失的现行证据）。每条元数据带 source: upstream|openrouter|observed 溯源标签；/v1/models 响应、router 调用前校验、dashboard 用量视图、配额/告警全部消费同一个对象。配一条治理规矩（核验并入本条）：能力元数据只在 aggregate_models 出生，其他消费面只许读、不许造；变更清单枚举全部消费面（contracts、tests、前端、docs）。CLI 挂起不阻塞请求的既有约束保持。

Basis

direct: models.py:95/105/120 三处 created: 0（声明与 CLI 路径只交换裸 id，元数据无车道）；models.py:177-182（上游元数据丢弃点）；dashboard-render-delegation-pattern.md（格式知识跨层重复必然漂移——specs 011/012/018/020 回归四次的根因）；integration-test-broken-after-sse-removal.md（消费面漏枚举的既往事故）。reasoned: 暴露层、路由层、告警层各自拼一份能力数据 → 同一模型在不同处口径不一致，排查成本随消费面数量平方增长。

Rationale

这是杠杆选择本身：方向 1/2/4/5 全部依赖「能力数据从哪流过」的决定。先把解析做成单点，未来每个消费面都是一次读取而非一次集成；三条来源的结构化升级同时解决「元数据没有附着位」的根因（字段丢弃只是症状）。它也把方向 1 的口径固定下来——字段只在一个地方成型，杜绝第四次、第五次跨层漂移回归。

Downsides

触碰三条来源的内部接口，改动面最大（fetcher 返回类型、CLI 解析、聚合、测试），是三条里唯一 High 复杂度；如果只想要「先看到数字」，它可以晚于方向 1 落地——但方向 1 的字段语义应该先按本条的 source 口径定义，避免返工。

4.[500k]/[1m] 后缀：从被静默剥除到被校验的能力协商

Confidence 65% Complexity Medium direct 元数据的第一个消费方
Description

router.py 现在把客户端（Claude Code 等）表达上下文诉求的 [500k]/[1m] 后缀静默剥除后路由到同一上游——用户的诉求被扔在地板上，信息双向缺失。改为：解析后缀为能力断言，与能力元数据比对——满足则剥除后缀正常路由；不满足则在调用上游前显式报错（或自动改路由到满足该上下文的部署变体），不静默截断。反方向闭环：后缀诉求与实际能力的偏差进遥测，反哺方向 5 的校准。暴露哪些字段由这个消费闭环倒推——它是能力元数据的第一个真实买方。

Basis

direct: router.py:9-13（_CTX_SUFFIX_RE 注释明说这是网关客户端表达 desired context length 的用法）、router.py:25 docstring 示例 xai/grok-4.6[500k] -> (xai, grok-4.6)、router.py:35（剥除点）；responses-chat-compat.md（不支持的能力要在调用上游前显式报错——仓库既定先例）。reasoned: 后缀是生产流量里已经存在的能力协商雏形，客户端在为上下文诉求付费表达，网关却单向丢弃。

Rationale

只暴露不消费的元数据是死数据。后缀闭环给了元数据第一个真实买方（校验基准），让「暴露哪些字段」从凭空设计变成按需倒推；同时把「选错上下文模型」从运行时静默事故（以为跑 1M 实际 128k 截断）变成调用前的显式错误。与方向 1 构成双向闭环。

Downsides

硬报错改变现网的宽容行为，可能打断今天「带后缀也能跑」的客户端——需要明确灰度或先告警后拦截；解析后缀到数值（500k → 500000）需要处理非标准写法；「或选更大变体」依赖部署变体的存在（与方向 2 的回填值联动）。

5.观测违规检测层：用真实流量抓「元数据错了」，不做自校准填充

Confidence 55% Complexity Medium direct + reasoned（已降格） 元数据质量回路
Description

spec 020 已按模型存 input_tokens/output_tokens/total_tokens。把观测聚合值用作违规检测而非能力填充：当真实流量出现超过元数据 context_length/max_output_tokens 的样本（或持续逼近上限的截断），判定元数据错了并告警。明确砍掉「用观测值自校准填充元数据」的原始版本——观测最大值只是能力的下界（实际流量几乎不探边界），拿它填充会系统性低估能力；唯一可靠的方向是「观测值越界 = 元数据错误」的单向检测。前置依赖：finish_reason 目前未落库，截断信号需要补上这一字段。

Basis

direct: 遥测字段已落库（spec 020：input_tokens/output_tokens/total_tokens，storage 层 T003 / data-model.md）；核验发现的事实缺口：finish_reason 未落库。reasoned: 回填值是第三方名义值、会漂移、档位会不同；而「观测到超过元数据上限的样本」是无歧义的反例信号——它不需要流量探边界，只需要一例越界即证伪，与自校准（需要系统性探边界）的证据要求完全不同。

Rationale

方向 2 的回填值（来自 OpenRouter 目录）可能与你的实际部署不符——名义值会漂移、档位会不同。本条是唯一能持续对元数据证伪的回路，且数据已经在库里（边际成本一条聚合查询）。它也是全场唯一不依赖上游配合的正确性信号源——Codex 空目录、Cursor 走 CLI 的场景里，网关自己的遥测永远在。

Downsides

被核验降格过：观测是下界不是上界，本条不能回答「这个模型的真实上限是多少」，只能回答「这份元数据是不是错了」；越界样本罕见，回路可能长期静默；finish_reason 落库是隐藏新增依赖（存储 schema 变更）；截断率类指标在该字段落地前不可用。

Rejection Summary

39 条原始想法（5 框架）→ 合并为 13 条候选 → 5 条存活。多框架重复命中在合并时计票（如「entry 加字段」被 4 个框架独立命中 6 次）。

#候选淘汰 / 归并原因
M2声明式 model_info 作为默认权威源（原形态）被更简的 OpenRouter 目录回填取代（实测覆盖 xiaomi/mimo、x-ai/grok、openai/codex 等主流模型，整目录一次拉取 + 缓存）；config 声明入口整体移除——不做配置兜底，目录外模型（cursor 侧car）直接省略字段。原三态语义（unknown/conflict）保留为回填链的省略纪律。
M6opt-in 形态协商（?expand=capabilities）并入 #1 备注。依据虚高：核验确认 tests/test_models.py:106-120 断言的是字段存在而非形状锁定；且 OpenRouter 先例本身就是无 opt-in 直加并生态无感——同一先例反证其必要性。可作短期上线保险，不值得单列。
M7body 级 capabilities 附录并入 #1 作为保守备选形态（errors 先例是已上线验证的零破坏路径）。与 entry 直加是同一字段集的放置位置之争，应开成一个议题而非三张选票。
M8双轨详情端点（/v1/models/{id}、Link rel=describedby）弱依据：download-request-json 教训的主旨是「能派生就别开新路径」，对本条实为反向证据；且深元数据去处与 M10 重复。作为附属问题并入 #1/#3 讨论（详情端点可为 curl 保留，消费方必须可降级）。
M10分层瘦身（深度元数据走独立可缓存资源）类比错位：OpenRouter 的分层是 entry 内部结构（top_provider 子对象），不是独立资源；目录体量小（条目数十级、每条几百字节），SC-001 延迟威胁不成立，拆出去收益趋近于零。
M11能力即运行时反馈（响应头 push x-otel-*）无外部先例（OpenRouter/Anthropic 均不做）；每响应加头 + CORS 暴露的持续成本换低频收益。「从不查目录的客户端」本来也用不上该信息。
M12能力即 id（[1m] 后缀升格为目录命名变体）承重外部依据待核实；更硬的内部反证：今天后缀被剥除后路由到同一上游，目录列 grok-4.6[1m] 变体等于承诺无执行机制的能力，恰违反「假元数据最可怕」。其反问「id 是标识符还是能力描述符」保留为会议挑战问题。
M9unknown/conflict 三态语义归并入 #2：它是「声明 > 上游」优先级规则的语义补全，脱离管线无法独立实施。
