Grounding Context

Codebase Context

Python 3.10+ FastAPI LLM API gateway (otel-agent) with React/TypeScript dashboard. DuckDB/SQLite storage.
Critical Gap
converter.py only handles text content parts. All 6 converter functions filter type=="text" and silently drop image_url/image blocks. No image generation endpoints exist. Dashboard blind to image content.
External Context
OpenAI: image_url content parts with url field (base64 data URIs or HTTP URLs). Anthropic: image content blocks with source field (type: "base64" or "url"). Formats are structurally incompatible — require active transformation, not passthrough.

Topic Axes

1. Multimodal chat content — image_url/image content parts in chat completion requests and responses
2. Cross-format image conversion — converting image content between OpenAI and Anthropic formats
3. Image generation proxy — new endpoint for /v1/images/generations
4. Image telemetry and dashboard — logging, storing, and displaying image-related requests
5. Streaming with image content — handling image content in streaming responses

1. Unified ContentPart Abstraction

Cross-format image conversion Conf 85% Cx M
Description
Introduce a single ContentPart union type with factory methods (from_openai, from_anthropic, serialize) that all 6 converter functions, message_parser, and logger consume. Today every function independently filters type=="text" and discards the rest — converter.py:27, message_parser.py:46, message_parser.py:194. Adding any new content type (images now, audio later) requires writing one converter, not touching 6+ files.
Basis
reasoned: Each of the 6 converter functions and 4 parser branches independently reimplements the same text-only filter; a shared abstraction eliminates this duplication and creates a single extension point.
Rationale
Highest-leverage single investment. Once ContentPart exists, every future content type plugs in at one location. Without it, each new type requires editing converter.py, message_parser.py, render.py, and logger.py separately — compounding maintenance cost.
Downsides
Requires refactoring all 6 converter functions and the parser. Risk of regression during migration if tests are insufficient (and currently there are zero multimodal tests).

2. Silent Image Stripping Fix

Cross-format image conversion Conf 90% Cx S
Description
Fix the core correctness bug: converter.py silently drops image_url content parts during cross-format conversion. The gateway returns a successful response but the upstream provider never sees the images. This is a correctness bug disguised as a feature gap — users get worse answers and blame the model.
Basis
direct: converter.py:27-30 — system message content array uses text-only flatten. converter.py:64-89 — anthropic_to_openai_request forwards content verbatim but formats are structurally incompatible. All 6 functions filter type=="text".
Rationale
Without this fix, the gateway actively harms quality while appearing healthy. Every multimodal request through a cross-format path produces degraded results with no diagnostic signal.
Downsides
The fix requires non-trivial transformation logic (restructuring source objects into data URIs). Must handle both base64 and URL source types. Testing is critical but currently absent.

3. Image Generation Proxy

Image generation proxy Conf 80% Cx M
Description
Add /v1/images/generations endpoint following the existing endpoint pattern in server.py (route decorator → parse body → resolve provider → forward). Users who need DALL-E or similar must call the provider API directly today, bypassing all gateway value: logging, auto-routing, rate limiting, cost tracking.
Basis
direct: server.py shows clear pattern for new endpoints. config.py supports provider api_format detection. No /v1/images endpoint exists in codebase.
Rationale
The gateway's value proposition is being a single entry point for all LLM operations. Image generation is a major LLM capability. Every call that bypasses the gateway is a missed data point and a missed auto-routing opportunity.
Downsides
Image generation APIs differ significantly from chat APIs (synchronous, larger payloads, different response shapes). Only OpenAI supports this endpoint — Anthropic and other providers don't have image generation APIs.

4. Image-Aware Auto-Routing

Multimodal chat content Conf 75% Cx M
Description
Fix classifier blindness to images (classifier.py:39-49 _extract_text_content filters to text) and add a Provider capabilities set (vision, image_generation) for routing decisions. A request with image_url gets routed to a vision-capable model, not one that silently drops the image.
Basis
direct: classifier.py:39-49 — _extract_text_content strips everything that isn't text. auto_handler.py routes by task classification alone — no image awareness.
Rationale
The auto-router's core promise is picking the right model. A vision request gets the same complexity score as text, potentially routing to a text-only model that can't process images — a functional failure.
Downsides
Requires updating the classifier, auto_handler, and config.py. Provider capability metadata must be maintained per provider.

5. Telemetry Body Decomposition

Image telemetry and dashboard Conf 70% Cx M
Description
Replace opaque string storage of request/response bodies with a decomposition layer that separates content payload from metadata. Today logger.py stores request_body and response_body as TEXT, and server.py truncates at 500 KB — which silently drops base64 image data. Decomposition extracts structured fields (model, image count, image sizes) while storing raw body separately.
Basis
direct: logger.py:28-55 stores as opaque TEXT. server.py:430,442 truncates at 500 KB. No image columns in RequestRecord schema.
Rationale
Once bodies are decomposed, you can query "how many image requests hit provider X" without parsing raw JSON. This powers cost attribution, quality dashboards, and debugging — three future capabilities from one infrastructure investment.
Downsides
Schema migration required for DuckDB and SQLite. Must maintain backward compatibility with existing data. Decomposition logic adds processing overhead on the write path.

6. Dashboard Image Content Lens

Image telemetry and dashboard Conf 65% Cx L
Description
Build a specialized rendering mode in the dashboard that extracts and displays image content: thumbnails for images in chat messages, side-by-side diff views for image generation requests, and a gallery view of all images processed in a time window. Makes visual content inspection trivial for operators.
Basis
direct: message_parser.py only extracts text. specs/016-llm-body-viewer/research.md documents "[Image content]" placeholder strategy. No <img> tags exist in frontend.
Rationale
The dashboard IS the product for observability. Without image display, any multimodal debugging falls back to raw JSON inspection — a friction point that discourages adoption.
Downsides
Frontend changes in React/TypeScript. Must handle large base64 payloads efficiently. Privacy considerations for displaying image content.

7. Content-Aware Streaming Frame

Streaming with image content Conf 70% Cx M
Description
Extend the SSE streaming pipeline to emit content-part-aware frames rather than raw text deltas. Currently streaming converters only map text_delta events — Anthropic's image_delta blocks produce None returns and are silently swallowed. Typed frames (content.text, content.image, content.tool_use) let the client demultiplex by type.
Basis
direct: converter.py:196-201, 219-224 — streaming converters only handle text_delta. server.py:302-405 yields untyped SSE lines.
Rationale
The streaming frame format, once standardized, becomes the backbone for any future real-time content type. Audio transcription, tool_use streaming, image generation progress — all become cheap additions.
Downsides
Changes the SSE wire format, which may break existing clients. Must maintain backward compatibility with text-only streams.
