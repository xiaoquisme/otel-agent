本机现场事实（本轮读取 ~/.hermes/auth.json）

已经存在 providers["openai-codex"]，带 auth_mode: "chatgpt"、 tokens: {access_token, refresh_token} 与 last_refresh。

注意一处更正：source: "device_code"、 label 与 base_url: https://chatgpt.com/backend-api/codex 不在 providers 条目上，而在 credential_pool["openai-codex"][0] 上——任何导入表都要把 json pointer 指进 pool 条目，只读 providers[...] 拿不到 base_url。

access token 是 JWT（iss=https://auth.openai.com、 aud=["https://api.openai.com/v1"]），命名空间 claim https://api.openai.com/auth 里带 chatgpt_plan_type: prolite 与 chatgpt_account_id。token dict 没有 expires_in/id_token/token_type，所以 xAI 形状的 token 校验 不能照搬（_jwt_exp() 仍可用）。Hermes 的 credential_pool 还带 priority、request_count、last_error_code/ last_error_reset_at——它已经建模了多账号池化与每条 grant 的配额重置状态；池注册表里 同时已有 copilot、xiaomi、openrouter、xai-oauth。

External context（2026-09-15，研究价值：高）

上游面：POST https://chatgpt.com/backend-api/codex/responses ——Responses API，不是 chat/completions。

请求头全部吃重：Authorization: Bearer； ChatGPT-Account-ID（规范 PascalCase，值取自 JWT 的 chatgpt_account_id claim）；originator + User-Agent ——Cloudflare 只放行 codex_cli_rs / codex_vscode / codex_sdk_ts / 任何以 Codex 开头的值，第三方取值即使 token 有效也会拿到 403 + cf-mitigated: challenge。

body 约束：强制 store: false，并要求 include: ["reasoning.encrypted_content"] 才能在轮次间携带状态；端点 拒绝 max_output_tokens 与 temperature（400）。

凭证：refresh token 一次性、每次刷新即轮换；出示已消费的 token 会触发 复用检测并撤销整个 grant family。Hermes 自己的 #22903/#7806 记录了这个：它导入了 ~/.codex/auth.json 的 refresh token 并自行刷新，「偷走了另一个客户端的刷新回合」， 永久废掉了 Codex CLI 与 VS Code 的会话；它的修法是自持 ~/.hermes/auth.json、绝不触碰 ~/.codex/auth.json。同类做法：CodexBar 用只读 token + CLI 独占刷新；OpenClaw 用「token sink」（唯一所有者，外部 CLI 材料只做一次性 bootstrap）；LangChain 的 ChatGPT OAuth 故意把 token 路径与 ~/.codex/auth.json 分开。 登录回调端口 1455 与 Codex CLI、opencode 相撞。

先例：CLIProxyAPI（Go，参考实现）、wowyuarm/codex-proxy、 @pikoloo/codex-proxy、opencode-openai-codex-auth（注册成 provider codex 而非 openai 以避开冲突）、go-llm-proxy、CodexBar。主流做法是 直接复用 OAuth token 走 HTTP，绝不 shell out。

对比 Anthropic：Anthropic 禁止第三方使用 Claude.ai Free/Pro/Max 凭证，其 2026-02-19 的消费者 ToS 更新禁止为第三方工具提取 OAuth token；那个生态的答案是架构性的—— 把 CLI 作为子进程拉起（claude --print），而不是复用它的 token。 OpenAI 的立场不同，所以同一个问题按厂商有两个相反的解法。

服务条款：2026-08-21 Codex/ChatGPT 负责人 Thibault Sottiaux 回应额度抱怨时表示， 受影响的用户多数在用 「sub2api」（订阅转 API 再分发），这违反 ToS 并触发反欺诈； 而通过「Sign in With ChatGPT」使用订阅是没问题的，第三方开源客户端（点名 Pi 与 OpenCode）也在内。界线是：个人代理可以，多用户分发不行。

限额：OpenAI 于 2026-08-25 恢复了 Plus 的 5 小时滚动 Codex 上限（六周前刚取消），Pro 层暂免（来源互相冲突）。

研究可信度：本轮研究环境无法直连 GitHub 与 raw.githubusercontent， 代码级断言（header 大小写、翻译表、PR 史）均为二手，实现前需用一次真实抓包核实； gpt-5.6-sol-900k 在任何公开来源中都查不到，疑似 Hermes 本地别名，不可硬编码。

请求腿的 header 未经脱敏就入库：把 telemetry 改成正名单

  • Axis upstream-identity
  • Confidence 92%
  • Complexity Low
Description

这是一个今天就存在、且与 Codex 无关的缺陷：server.py:622 的响应腿 会过 redact_sensitive_headers，而 :623 的请求腿直接把 dict(request.headers) 原样落库；脱敏名单本身也只是一张三名黑名单 （logger.py:8：authorization、x-api-key、 set-cookie）。所以客户端发来的 Authorization、 originator 或 chatgpt-account-id 会一字不改地进 SQLite， 而 dashboard 绑在 0.0.0.0 且没有登录（dashboard login 是明确 out of scope）。 修数据泄漏与修策略形状是同一件事：把存储改成正名单（只存有人声明的 header）， 把身份性 header 名补进集合，并把出站身份做成单向阀——网关从 vault 自己设 originator/User-Agent/ChatGPT-Account-ID/ OpenAI-Beta，丢弃入站值（客户端自带的 originator 既是伪造向量， 也是封号向量）。同时 telemetry 仍要能回答「我们实际上游发了什么」。

Basis

direct:server.py:622-625 （stored_headers = redact_sensitive_headers(resp_headers) 对请求腿不适用， stored_request_headers = dict(request.headers) 原样）； logger.py:8,11-17 三名黑名单与替换函数； server.py:62 的 httpx 客户端未设默认 header（出站 UA 是 httpx 自己的）； tests/test_server.py:108-119 只覆盖响应腿。

external:account id 是一个稳定的账号标识符， 即 credential-adjacent——它不是「某个 key 被花掉了」，而是「这个 grant 失去了匿名性」。

Rationale

黑名单只保护「有人记得住」的那些 header，而记录 schema 正要长出新的敏感名字。而且这条不依赖 任何 Codex 假设：即便这次 Codex 一行不写，泄漏也已经在发生。它是唯一一条头条本身就是可现场 复现缺陷的候选——验证者独立读过 server.py:622-623 与 tests/test_server.py:108-119，并指出它比陈述更严重：客户端 Authorization 同样明文入库。

Downsides

正名单会让历史库里已有的列语义发生变化，dashboard 的 header 视图可能少显示一些今天能看到的东西 ——这是有意的，但需要在 UI 上说清楚。把身份 header 补进正名单后，「我们发了什么」只能靠出站侧单独记录， 不能靠入站副本。

2

让刷新路径对「一次性轮换 token」安全

  • Axis credential-lifecycle
  • Confidence 88%
  • Complexity Medium
Description

对 xAI 那套约 6 小时寿命的 token，今天的刷新够用；对 Codex 的一次性轮换 token，它是 会永久毁掉账号状态的。三件事必须一起做：

(a) host 绑定。_token_endpoint 只在 host 以 x.ai 结尾时才采用存储的 endpoint，否则重跑 xAI discovery 并最终硬编码 https://auth.x.ai/oauth2/token。一条 Codex grant 的刷新 POST—— 连同 refresh token——因此被发往另一个厂商的 auth host，而失败信息还是 xAI 措辞的。 必须拒绝把 refresh token 发往任何非「保存时记录的」host，永不回落到厂商默认值。

(b) 单飞 + fencing + 持久化提交。今天刷新是 with _lock: 里一次同步 httpx.post，在 _atomic_write 之前；_lock 是模块级进程内锁。窗口里崩溃、proxy restart 时的 SIGTERM、磁盘写满、20s 超时——任何一种都会让 vault 停在一个已经在上游被消费掉的 refresh token 上，下一次刷新就触发复用检测、撤销整个 grant family。改成异步单飞（一个刷新者、N 个 等待者）+ vault 里持久化的 generation + 「比盘上旧就不写」的 CAS。顺带修掉 :190 的 new_refresh = ... or refresh：上游若没在响应里带回新的 refresh token，这行会静默保留那个已被消费的。并给一个明确的惰性模式： expires_at <= 0 今天已经意味着「永不刷新」，但 save_grant 恰好拒绝 没有 refresh token 的 grant，所以这个最安全的模式反而不可达。

Basis

direct:auth_vault.py:24（模块级 threading.Lock()）、:95-96（无 refresh 即拒绝）、 :142-143（if expires_at <= 0: return False）、 :150-164（host 判定与硬编码回落）、:184-187（xAI 措辞的失败串）、 :190（静默沿用旧 refresh）、:214-229（锁横跨网络调用，写在其后）； AGENTS.md:15（install 不 restart 仍是旧进程——本仓库有文档化的双进程现实）。

external:Hermes #22903/#7806（导入 ~/.codex/auth.json 的 refresh token 并自行刷新，永久废掉 Codex CLI 与 VS Code 会话）； token sink 模式；OAuth 2.1 的单次使用轮换语义。

身份与凭证同源派生：credential 从字符串变成一个 record

  • Axis upstream-identity
  • Confidence 64%（活体探针后下调）
  • Complexity Medium
Description

Codex 要 originator/User-Agent（Cloudflare 只放行 codex_cli_rs/codex_vscode/codex_sdk_ts/Codex 开头的值）与 ChatGPT-Account-ID，这三样今天都表达不出来： AUTH_HEADERS 是按 api_format 索引的两项字典、只返回 {"Authorization"}；build_request_headers(provider) 没有第二个参数； models.py:83 另外另建了一份 {"Authorization": f"Bearer {resolve_bearer(provider)}"} 绕开注册表（所以 /v1/models 会不带任何身份头出去）；而且没有任何测试断言过发往上游的 header。把凭证解析改成返回一个 record——{bearer, claims, generation}—— 在保存时解析一次、并把一块非秘密的 identity 块持久化在 token 旁边，这样任何展示面 都不必触碰秘密。账号头与 bearer 从同一次解析同源派生，因此永远不可能互相不一致； 当 claim 缺失或畸形时直接不发这个头，让上游回 401，而不是让网关呈现一个看似合理 的身份、然后换来一个误导性的 403。

direct:provider_utils.py:7-10,36,41（两项 AUTH_HEADERS、builder 签名、按 api_format 直接索引）；models.py:83 （分叉的第二份 header 构造）；logger.py:8；auth_vault.py:36-46 （唯一的 JWT 解码器只读 exp）；src/ 里 originator 与 ChatGPT-Account-ID 出现 0 次；build_request_headers 在 tests/ 里 0 命中（验证者独立确认）。现场：token 里确有 chatgpt_plan_type=prolite、chatgpt_account_id、client_id、 scp，今天全部被丢弃。

external:Cloudflare 的 originator 白名单与 cf-mitigated: challenge（二手；白名单取值经独立检索互证，但无一手源）； TLS-JA3 / UA 门控的同类结构——伪造第一方指纹在指纹轮换之前有效，而它正是「非官方使用」最容易被读到的 信号。

reasoned:身份与凭证是同一次解析的两个视图。任何让它们 分开旅行的设计，都允许「两者不一致」这个 bug 存在，而上游对这种不一致给出的错误， 与「你的订阅没有权限」无法区分——恰恰是这个功能最不能搞错的那句话。一个佐证： token 的 aud 是 https://api.openai.com/v1，而 surface 是 chatgpt.com/backend-api/codex，所以身份 claim 与端点不能互相推导， 必须一起携带。

Downsides

活体探针后修订——本条被削掉一半

初稿把这一条列为「grounding 自己称作实现风险最高」的一项，理由是 Cloudflare 的 originator/User-Agent 白名单会让第三方身份即使持有效 token 也吃到 403。 本机实测否证了这条门槛：以 originator: otel-agent + User-Agent: otel-agent/0.1 请求得到 200 与完整 SSE 流，无 cf-mitigated: challenge；而且连 ChatGPT-Account-ID 都可以省略。

配额成为一等状态：类型化 ledger + 按重置时间准入

  • Axis entitlement-boundary
  • Confidence 80%
  • Complexity High
Description

今天是「entitlement 只是展示」：rewrite_xai_error 被 status != 403 挡住，所以 429 在任何地方都没有被分类过；流式路径 连改写都没有，把上游的 error body 原样塞进 SSE 帧。而一条 Codex 请求可以用五种方式 失败，全都表现为同一个不加区分的 403——token 已死、账号没有 Codex 权限、Cloudflare 指纹挑战 （它会带着一个完全有效的 token 到来）、plan 档位不满足、区域限制——外加 5 小时滚动上限带来的 429。

在请求行上加 grant_id/auth_mode 列与一个类型化结果 （entitlement_denied / quota_window_exhausted（带 reset_at）/ fingerprint_challenged / transport）， 在上游响应被看到的那一处只分类一次，并且在任何改写之前记录， 让记录保持为证据。然后使用它：每条 grant 一个 {until, reason, source} 门，其截止时间学自上游自己的 Retry-After／重置时间戳；处于门内时网关停止发送并立即带着重置时间回答 ——这是忙音，不是断路器（断路器数失败次数，这个存的是上游告知的截止时间）。 2026-08-25 恢复的 5 小时上限是一个真实会重置的资源，它会以未分类的 429 形式出现；Hermes 已经把这个 形状写下来了（last_error_code/last_error_reset_at）。

Basis

direct:xai_errors.py:23-34 （if status != 403 or not isinstance(body, dict): return body，三条 Grok 子串匹配）； server.py:420-425（非流式路径）与 :455-471（流式路径无改写钩子）； storage/sqlite.py:57-70,81,225（requests 列里没有 grant/账号列， GROUP BY model_name 聚合）；auth_vault.py:120-132 （get_status 只有 logged_in/path/imported_from/ expires_at）；commands/doctor.py:73-77； plan 004 :99,118,120（KTD5「403 改写只是展示」+ defer 掉的 live entitlement probe）； specs/020:104（配额明确 out of scope）；c5d4a0e（breaker 真的被删了）。

external:电话网 trunk-group 忙音（呼叫方学到的是 「忙到什么时候」，不是「呼叫失败」）；RFC 9110 Retry-After； Envoy outlier detection（按时长弹出而不是按次数）；5 小时上限恢复。

reasoned:对一个按时计费的 key，重试 429 几乎免费； 对一个跑在滚动窗口上的订阅 grant，重试花的正是它等待的那份预算。「出错就重试」的反射在这里 是有害的，而合适的工具是带过期时间的状态，不是带阈值的计数器。

Rationale

它把最令人困惑的用户可见结果——「一小时前还好好的，现在什么都 403，重新登录也没用」 （README 已经不得不用一整句散文去解释它）——变成一个自解释、自清除的状态。这也是唯一一条让 网关成为比裸 CLI 更好的订阅客户端的想法。它有意不复活 c5d4a0e 删掉的断路器：那是按次数开闸，这个是存上游给的截止时间。

Downsides

这是全套里最贵的一条（新列 + 分类器 + 门状态 + UI 暴露），而且存在范围滑移的风险—— 「ledger 离 router 只有一步，而 router 刚被有意删掉」。另外它要用的 doctor --probe 已被第 5 条吸收（那条的探针同时解决指纹分诊），所以这里的净增量是 ledger 与准入控制。 前提事实（5 小时上限及其按账号范围）两手来源对 Pro 层自相冲突，见待核实清单第 6 条。
